Setup ambiente lavoro da VSC terminal
--------------------------------------

1. Crea la cartella del progetto
mkdir OrchidVerse_project
cd OrchidVerse_project

2. Inizializza Git
Permette di tracciare il progetto.
Dentro la cartella appena creata:
git init

3. Crea e attiva l’ambiente virtuale
python -m venv venv
venv\Scripts\activate         # Windows

4. Installa Django
pip install django

Puoi anche salvare le dipendenze:
pip freeze > requirements.txt

5. Crea il progetto Django
django-admin startproject OrchidVerse .

Il punto `.` serve per creare il progetto nella cartella corrente.

6. Crea l’app `OrchidVerse`

python manage.py startapp orchid_verse

Registrare 'orchid_verse' (app name) nella variabile INSTALLED_APPS del settings.py del progetto.
ossia in OrchidVerse/settings.py
INSTALLED_APPS = [ ...]

7. Aggiungi il modello `Orchid`

Nel file `orchid_verse/models.py`:

from django.db import models

class Orchid
  pass

*** cuando fai modifiche al modello, sempre questi due commandi:
python manage.py makemigrations OrchidVerse
python manage.py migrate

8. Crea un branch (opzionale ma consigliato)
Se vuoi lavorare in modo ordinato:
git checkout -b gestione-orchids

9. Fai il primo commit
git add .
git commit -m "Setup iniziale progetto Django con modello Orchid"

10. Collega al tuo repository GitHub
Crea un nuovo repo su GitHub (vuoto, senza README)
Poi nel VSC terminal:

git remote add origin https://github.com/tuo-utente/nome-repo.git
git push -u origin gestione-orchids

## 🧭 Dopo il primo push: come procedere con Git

### ✅ 1. Continua a lavorare sul branch attuale
- Se stai ancora sviluppando una funzionalità (es. gestione delle orchidee), **continua sul branch `gestione-orchids`**.
- Fai commit regolari ogni volta che completi un piccolo blocco di lavoro:
  ```bash
  git add .
  git commit -m "Aggiunta form per inserimento orchidee"
  ```

### 🌿 2. Quando creare un nuovo branch?
Crea un nuovo branch quando:
- Inizi una **nuova funzionalità** (es. autenticazione utenti, dashboard, API).
- Vuoi **testare una modifica** senza toccare il codice stabile.
- Hai finito una funzionalità e vuoi **ripulire il codice** prima di unirlo.

Esempio:
```bash
git checkout -b autenticazione-utenti
```

### 🔁 3. Quando unire con `main` (o `master`)?
Unisci il tuo branch quando:
- La funzionalità è **completa e testata**.
- Hai fatto commit chiari e ordinati.
- Vuoi **rendere stabile** quella parte del progetto.

Passaggi:
```bash
git checkout main
git pull origin main         # aggiorna il main locale
git merge gestione-orchids   # unisci il branch
git push origin main         # aggiorna il main remoto
```

### 🧼 4. Dopo il merge: cosa fare del branch?
Hai due opzioni:
- **Mantenerlo** se pensi di continuare a lavorarci.
- **Eliminarlo** se la funzionalità è chiusa:
  ```bash
  git branch -d gestione-orchids        # elimina localmente
  git push origin --delete gestione-orchids  # elimina su GitHub
  ```

## 🧠 Best practices per il tuo flusso Git

| Situazione                         | Azione consigliata                         |
|-----------------------------------|--------------------------------------------|
| Inizio nuova funzionalità         | `git checkout -b nome-funzionalità`        |
| Fine funzionalità                 | `git merge` nel branch principale          |
| Bugfix rapido                     | Puoi farlo direttamente su `main` se urgente |
| Collaborazione o test             | Usa branch separati                        |
| Ogni 1–3 commit                   | Pusha su GitHub per backup e tracciamento  |

## 🧬 Struttura del flusso Git per Orchid Assistant

### 🔹 Branch principali

| Branch        | Scopo                                                                 |
|---------------|-----------------------------------------------------------------------|
| `main`        | Versione stabile e funzionante del progetto                          |
| `dev`         | Ambiente di sviluppo integrato (merge di funzionalità testate)       |

### 🔸 Branch funzionali (feature branches)
Ogni nuova funzionalità vive nel suo branch, derivato da `dev`:

```bash
git checkout dev
git checkout -b feature/nome-funzionalità
```

Esempi:
- `feature/orchid-models`
- `feature/weather-integration`
- `feature/admin-customization`
- `feature/care-logic`

---

## 🔁 Flusso di lavoro quotidiano

### 1. **Crea un branch funzionale**
Quando inizi una nuova funzionalità:
```bash
git checkout dev
git checkout -b feature/care-logic
```

### 2. **Lavora e fai commit regolari**
Ogni commit descrive chiaramente cosa hai fatto:
```bash
git add .
git commit -m "Aggiunta logica base per consigli di irrigazione"
```

### 3. **Pusha il branch su GitHub**
```bash
git push -u origin feature/care-logic
```

### 4. **Apri una pull request verso `dev`**
Quando la funzionalità è pronta e testata:
- Vai su GitHub → apri una PR da `feature/care-logic` verso `dev`
- Scrivi una descrizione chiara della modifica

### 5. **Unisci su `dev`**
Dopo revisione e test:
```bash
git checkout dev
git pull origin dev
git merge feature/care-logic
git push origin dev
```

### 6. **Release su `main`**
Quando vuoi pubblicare una versione stabile:
```bash
git checkout main
git pull origin main
git merge dev
git push origin main
```

---

## 🧠 Branch speciali (opzionali)

| Branch             | Scopo                                                                 |
|--------------------|-----------------------------------------------------------------------|
| `hotfix/...`       | Correzioni urgenti su `main`                                          |
| `experiment/...`   | Prototipi o test non destinati alla produzione                        |
| `docs/...`         | Documentazione, README, tutorial                                      |

---

## 🧼 Pulizia e manutenzione

- Elimina branch locali e remoti dopo il merge:
  ```bash
  git branch -d feature/care-logic
  git push origin --delete feature/care-logic
  ```
- Usa `git log --oneline --graph` per visualizzare la storia
- Tagga le versioni stabili:
  ```bash
  git tag -a v1.0 -m "Prima versione stabile"
  git push origin v1.0
  ```
